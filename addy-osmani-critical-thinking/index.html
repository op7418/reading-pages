当 Agent 替你干活时，如何保持批判性思考

Critical thinking when agents do the work —— 工作可以卸载，责任不能

原文：Addy Osmani《Critical thinking when agents do the work》，X Article，2026.11.03 发布。原文链接：x.com/addyosmani/status/2117512471930167… 。本页为中文导读与解读，不是全文翻译；引号内为少量关键句的中译，版权归原作者。

01

一分钟速读

作者自称是 Agent 工作流的重度支持者，他写这篇文章不是劝人少用 Agent，而是提醒：模型越强，明显错误越少，输出越“看起来对”，人就越容易放松警惕。他把人对 AI 的依赖分成“认知卸载 → 顺从 → 认知投降”三档，并给出一组自问清单、验证习惯、审查方法和日常练习，核心结论是：工作和大部分审计都可以交给 Agent，但责任交不出去。

02

开篇：问题与答案之间的空间被压缩了

  • 过去批判性思考靠“谦逊的好奇心 + 适度怀疑”来训练。作者说这依然成立，但当大部分工作都经由 Agent 完成时，日常里已经没有什么会“逼”他去做批判性思考。
  • 他明确表态自己是这类工具的忠实用户，写作目的不是倡导减少 Agent 工作流，而是帮人在“什么都能甩给 Agent”的环境里保住批判性思考。
  • 过去大部分认知和审美加工，发生在“提出问题”与“得到答案”之间；现在这段时间只剩几秒。
  • 反直觉的一点：模型越进步，明显错误的比例越低，多数输出写得好、基本正确，但不会让你想再看一眼。
  • 即使同时跑很多个 Agent，看输出的仍然只有你这一双眼睛。
  • 难以自我纠偏的另一个原因是：Agent 工作流让人愉快，快速、舒服、常常正确的答案，恰恰让人放松警惕。

引文：“你必须把批判性思考主动安排进一天里，因为默认情况下，没有任何东西会替你做这件事。”

03

卸载、顺从与投降

  • 作者把依赖程度描述成一条光谱：
  • 顶端是认知卸载（cognitive offloading）：把任务交给 AI，但结果的所有权仍在你手里。他每天都这样做，也建议读者这样做。
  • 中间是顺从（deferral）：工具的输出直接变成你的新输入，结果不再被当作“待验证的假设”。
  • 底端是认知投降（cognitive surrender）：AI 的输出悄悄变成了你自己的观点，你不再觉得需要检查。
  • “认知投降”一词来自沃顿商学院的 Steven Shaw 和 Gideon Nave。随着信任（或懒惰）增加，人会沿光谱下滑，而且每一步都很渐进、看起来很合理：上一个答案认真读了，下一个就略读，再下一个只扫结构，最后被问到某一行时，连借助 Agent 都解释不清。
  • 这就是认知债务累积的方式，通常在你试图调用对系统的心智模型、却发现它根本不存在时才暴露。作者提到 Margaret-Anne Storey 写过团队层面“共享系统理论”的侵蚀，他自己写过代码层面的“理解债务”（comprehension debt，术语来自 Jeremy Twei）：代码库看起来整洁、测试全过，直到要改系统时才发现没人懂它了。只看了目录就签字通过的策略文档或需求文档也一样。
  • 他强调不是要求做不到的事：大型现代代码库本来就不可能装进脑子。Claude Code 团队公开说过他们“按需重建理解”，要用到哪一块就让 Claude 解释哪一块。这类债务比多数工程师以为的更可恢复，关键是要知道自己缺什么。
  • 低风险的事可以完全委托。他举例：录课时要从三家评分相近的酒店里选一家，他直接让 AI 决定，效果不错，下次还会这么做。但投资、给孩子的职业建议、工作中“做什么、影响哪些用户、能不能上线”这类决定，他不会这样交出去。

引文：“在犯错代价低的地方放手交接；在后果要由别人承担的地方，把推理留在自己手里。”

04

我会问自己的问题

  • 以前不知道自己怎么想时，他会回到一组基础问题：我在解决对的问题吗？方法对吗？有证据支持结论吗？怎么知道做完了？本质就是 5W1H，写出来幼稚，但能逼你从平时忽略的维度思考。现在很容易跳过这些，直接问 Agent 该怎么做。于是他有了新版本的问题：
  1. 提问之前，我有没有先形成假设？ 在任何非平凡任务前先写下（哪怕只在脑子里）自己猜的答案，猜错也没关系；因为读完一份写得漂亮的回答后，就很难想象别的可能。完全没头绪时，可以请模型做 Thariq Shihipar 说的“盲点扫描”（blind spot pass）：把你知道的告诉模型，让它找出你“不知道自己不知道”的东西。
  2. 我是在让它帮我思考，还是让它替我思考？ 两者都可以，只要清楚自己在做哪一种。
  3. 要让这个结论错，什么必须为真？ 然后去验证。模型对自己置信度的评估，远不如一个能实际执行的测试有价值。
  4. 我有没有从另一个角度听过反方观点？ 在开放性问题上立场很硬时，他会让不止一个模型去论证反方，再自己形成判断，耗时更长但理解更深。
  5. 我敢不敢当着将来维护它的人的面为它下注？ 适用于代码和任何交付物，他认为这是“可问责性”的标准。
  6. 我不再练习的是什么？ 比如一些日常调试，可以放掉，但要是有意识地放掉。
05

把验证变成习惯

  • 作者认为瓶颈已经从“写代码”转移到“确信自己是对的”。给 Agent 验证手段（端到端测试、属性测试、真实的应用交互），它就能在你看之前完成“改动 → 跑验证 → 读输出 → 再试”的循环。Boris Cherny 称之为“给 Claude 一种验证自己工作的方法”。你的角色从逐行阅读，变成搭建这些循环并审查证据。
  • 但验证本身也会被“投降”：“有证据支持我的结论吗？”退化成“检查变绿了吗？”。Agent 让写测试变得极便宜，你会看到大量绿色，但测试可能根本抓不到坏掉的功能；如果测试和功能犯了同一个错，它照样通过。而且一个绿勾只证明一个性质。

引文：“每看到一个绿勾，说出它检查了哪个性质；再说出一个它没检查的。”

  • 事先定义“已验证”，因为事后你会为任何结果找理由。Agent 工作的终点应当是具体的东西：测试通过、截图、日志或 trace，而不是“看起来做完了”。收到 Agent 的完成通知时，先看它执行的命令和输出，再看总结。
  • Claude Code 可以用一个全新上下文的子 Agent 自我批评，值得固定进循环里每次都跑。他自己每次完成复杂功能后还会问一句“我漏了什么吗？”，前沿模型常常会再补出两三件事。
  • 不必每件事都深挖，判断何时深挖本身是一项技能。他最喜欢 Claude Code 团队代码审查文章里的经验法则：如果你说不出这些检查会漏掉什么，就去要一次真正的审查，而不是快速批准。
  • 这也适用于代码之外：Agent 总结了五十通客户电话或一份竞品分析，就抽查几份原始材料；推荐所依赖的关键数字，核一下算法。
  • 收尾一句：Agent 让搭建验证变得便宜，难的是知道好的验证长什么样。
06

真正去看生成了什么

  • 场景：Agent 交来一个 600 行的 PR，你大致看看结构，变量名合理、测试通过，就批了。但中间可能藏着事务边界里一个细微的顺序变化，或某个边界情况的默认值被翻转。你确实审过，但只审出了你本来就知道要找的东西。
  • 写代码和审代码是两种技能，审查会在某个点变成橡皮图章。要像“这不是 AI 写的”那样读 diff，并越过 diff 去看 Agent 替你做了哪些决定：默认值、什么算范围外、两条需求冲突时它重新解释了哪一条。
  • 一份“一切顺利”的总结里看不到这些，所以要让它列出所做的决定和假设，然后自测：随机挑几行问自己“这一行呢？”；文档就合上后凭记忆写出主论点。有人在长会话后让 Claude 写一份变更报告并在末尾出测验，规则是“满分通过才合并”。
  • 要理解你交付的东西到足以为它辩护的程度，因为迟早有人会问。
  • Agent 也能帮你守护注意力：他维护的开源项目 PR 很多，他用 Agent 判断哪些是新进来的、哪些违反规范、哪里需要他关注，但很少让 Agent 自行决定，只用来缩小范围，再自己思考这些改动是否以正确方式解决正确的问题。
  • 然后是产量问题。作者称之为“编排税”（orchestration tax）：Agent 产出的量与你愿意署名的量之间的差距。如果完成的工作堆积得比你处理得快，再开一个会话也没用，要么收紧检查让更少的东西需要你，要么放慢。

引文：“当你产出的东西多于你能担保的，你就不再是在审查，而是在祈祷。”

07

好输入，好输出

  • 人的心智模型仍在参与，只是从“中间”移到了“两头”：前端是任务描述和上下文，后端是审查输出。所以作者把好的提示词视为一种批判性思考技能。
  • 过去需求含糊时，会有人追问，你才发现“其实我没想清楚”。Agent 往往不会拦你，它会补全你没说的部分，交回一个看起来已完成的东西，背后的想法却仍然模糊。他称之为“意图债务”（intent debt）：那些隐含的目标、约束和理由。和别的债务不同，这笔债没人能替你还，意图只能来自你。
  • 你的提示词反映你对问题的理解；表达不清，可能是脑子里本来就不清。
  • 建议：求助前先用自己的话写需求简报，说明受众、范围外事项、完成标准；第二轮修正还不到位，就别再微调，重写提示词。
  • 作者引用 Andy Clark 对“委托给 AI”与“与 AI 协作”的区分：协作时是相互放大的良性循环，提示词改善输出，输出改善下一次提示词，也改善你对问题的心智模型。不清楚时让 Agent 反过来采访你；会话结束时你自己的理解变清晰了，就是成功的标志。
  • 小心输入链：每个 Agent 都把上一个 Agent 的总结塞进上下文，很快第三个 Agent 就根本没读过原始文档。
  • 输出也要有自己的标准。他在很多创作媒介上玩过 AI，大部分作品从未展示，因为不达标。现在一切都格式漂亮、语气自信，“精致”已不再是有效信号。
  • 不达标时，把原因记进共享配置、hook 或测试里，避免重犯，这就是品味的复利。

引文：“AI 也许让产出变快了，但如果我不愿意把它署上我的名字，我就不会发出去。”

08

“但模型以后会比我更擅长这些”

  • 作者承认：如果你像他身边很多人一样看好这个领域，可能早就在想，一两年后模型就能发现我能发现的问题，何必维持这项技能？
  • 他同意很多检测工作会交给 Agent，他自己也在推动这一点。但最终总有人要为上线的东西负责，无论 AI 帮了多少，承担责任的必须是人。
  • 对某项任务该信任 Agent 多少，本身就是判断题；保持校准的一部分就是审查工作，因为模型出错的方式一直在变。Anthropic 对自家工程师和研究员的调研把这称为“监督悖论”：监督 Claude 所需的编程技能，恰恰可能因过度使用 AI 而退化。
  • 更好的模型解决不了的问题：你在做什么、为什么值得、影响谁、愿意牺牲什么。Agent 可以帮你梳理，但答案仍是你的。

引文：“你可以卸载工作，甚至卸载大部分审计，但卸载不了责任。”

09

日常可用的做法

  • 不必全部严格执行，挑适合自己工作流的用。
  • 每周一次：不用 Agent 写一点代码，或做一件“忘了怎么做会很糟”的真事。作者称之为校准练习，并说明不是道德意义上的。
  • 每月一次：写下自己已经不再做的事，决定哪些可以接受不做。他旧博文里的一个问题依然有效：如果 AI 不存在，你会有多迷茫？
  • 遇到超出理解的东西就去学。写作时碰到没见过的短语，与其搜一句解释塞进去，他更愿意花点时间真正弄懂它在体系里的位置。
  • 认真检查机器的产出是真实的工作量，假装它不费力，团队就会不做。把它当成一项排期任务。
  • 不再练习的技能会消失，而且可能比你想的快。不愿放弃的，就持续练。
10

带走什么

作者在结尾给出一份清单，大意如下：

  • 有意识：Agent 能测验你、采访你、给你看证据，但前提是你主动设置。
  • 诚实面对自己在光谱上的位置：借助 Agent 都解释不了答案，就是已经投降了。
  • 先有假设：提问前先形成一个，哪怕很烂。
  • 绿勾只代表一件事：它查了什么？没查什么？
  • 找证据：先看它跑了什么、返回了什么，再看总结。
  • 读出它的决定：它替你决定了什么？
  • 打磨提示词：你怎么写提示，暴露你对问题理解多少。
  • 设定标准并坚持：不愿署名的，就不发出去。
  • 最后的建议：提问前写下你预期会发生什么，Agent 做完后写下一件它没检查的事，看看这会不会改变你阅读输出的方式。独立思考，问更好的问题，为结果负责。
11

解读：背景

以下为本页整理者的解读，不是原文内容。

  • Addy Osmani 是 Google 的工程负责人，长期写开发者体验相关内容，近一年在博客和 Substack 上连续写了 Agent 编程相关的系列文章。本文把他此前提出的几个概念串到了一起：理解债务、意图债务、编排税、Agent 验证、技能退化，可以看作这一系列的“总纲”。
  • 文章的出发点不是“AI 会犯错”，而是相反：AI 错得越来越少、越来越隐蔽，于是人类审查的动力和能力同时下降。这是 Agent 能力提升后才凸显的新问题。
12

解读：关键概念白话版

  • 认知卸载 / 顺从 / 投降：区别不在于“交没交给 AI”，而在于结果在你心里的地位。卸载时它是待检验的草稿；顺从时它成了你下一步的前提；投降时它成了你的观点。判断标准很简单：借助 Agent，你能不能解释它？
  • 理解债务：代码能跑、测试能过，但团队里没人真正懂它。平时看不见，要改动时才爆发。
  • 意图债务：你没说清楚的目标、约束和理由，被 Agent 用“合理的默认值”悄悄补上。产物看起来完整，但不一定是你要的。
  • 编排税：同时开很多 Agent，产出暴涨，但你能认真审、敢署名的量没变。中间的差额就是税，不交就是在“祈祷”。
  • 监督悖论：监督 AI 需要的技能，正是过度依赖 AI 会让你丢掉的技能。
13

解读：为什么重要

  • 对个人：多开 Agent 的边际收益，最终会被“你能担保多少”卡住。审查和判断力是新的瓶颈，也是新的护城河。
  • 对团队：绿色 CI、整洁的 PR、漂亮的总结都不再可靠地代表质量，需要把“查了什么、没查什么”变成显式流程。
  • 对非工程工作同样适用：调研总结、竞品分析、策略文档，都可能出现“只看目录就签字”的投降。
14

解读：可以马上用的做法

  • 每次给 Agent 派非平凡任务前，先写一句“我预计结果是……”。
  • 把“完成标准”写进任务描述：要哪条测试通过、要哪张截图、要哪段日志。
  • Agent 完成后，先看命令和原始输出，再看总结；让它列出“做了哪些决定和假设”。
  • 每个绿勾后面补一句“它没检查的是……”。
  • 不达标的产出，把原因写进项目规则、hook 或测试，让品味沉淀下来。
  • 定期不用 Agent 做一件关键小事，确认自己的手感还在。
